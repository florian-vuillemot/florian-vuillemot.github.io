## OneLake

The data storage abstraction of Microsoft Fabric.
Data put in it is accessible to all the services in the fabric.
Data may not be physically stored in OneLake, in that case, OneLake create a "shortcut" that will point to the real physical location of the data.

It is a lakehouse, a combination of a data lake and a data warehouse supporting SQL and Spark.


Data loading:
- DataFactory
- Dataflows Gen2 based on Power Query.
- Notebooks
- Upload files

Data exploration:
- Lakehouse with interaction on tablees, files and folders
- SQL query from analytics endpoint.

with shortcuts, users permissions are used in belhaf of OneLake.

OneLake is in a tenant. A tenant can have multiple capacity associated (FabricSKU).
OneLake can have multiple Domain containing group of workspace.
In OneLake each ressource are items (data warehouse, data pipelines, etc.).

## Spark

There is a default Spark pool in the workspace. It can be configured with different option:
- Node familly: type of node (memory optimized, etc.)
- Autoscale: number of nodes min and max
- Dynamic allocation: number of executors

Environment as library or spark runtimes can be defined.
Native execution engine can be used to improve performance. It is vectorized processing engine running directly on the lakehouse infrastructure.
MLFlows integration.
Can define spark job definition to run on a schedule with different argument in parameters.
Spark jobs and Notebook can be scheduled.

By default, Fabric enable the "V-order" feature to optimize the reading operations by Power BI, SQL, and even Spark by sorting and ordering parquet files.


## Data Movement

**Pipeline** encapsulate sequences of **activities** that perform data movement.
An **activity** can be a data tranformation/movement or a control flow.

## Dataflows

It's a type of ETL for data preparation.
It can be used by data engineers or data scientists and create the semantic model.
In Fabric, tools like Power Query are used to create dataflows and graphically design query and diagram help the analysis and understanding.

## Data Warehouse

Consists of:
- Data ingestion
- Data storage
- Data processing
- Data analysis and delivery

Contains:
- Fact tables:
Contains numerical data to analyze.
They contains a large number of rows and are the primary source of data for analysis.
Ex: Total amount paid for sales  orders at a date.
- Dim tables:
Contains descriptive information about the fact tables,business entities.
it's the "who,what,where,when,why" of the datawarehouse.
Provide context for fact tables.
Generally, they are smaller than fact tables.
Also contains at least one unique identifier for each row generated automatically (**surrogate key**) but also an **alternate key** which is a natural or business key (often the ID of the transactional system).
Ex: Information about the customers who placed sales orders.
Some dim tables are **slowly changing dimensions** (SCD) which means that the data in the table changes over time and ensuring data stay up to date.
 - "Type 1" (overwrite the old data)
 - "Type 2" (add a new row with the new data)
 - "Type 3" (add a new column with the new data).
 - Type 4: add an new dimension.
 - Type 5: it's type 2 but for dimension too large.
 - Type 6: combination of type 2 and type 3.
And their is also "time dimensions" which are used to simplify time analysis.

Data warehouse use de-nomalized data model to reduce the number of joins needed to query the data.
Using **star schema** or **snowflake schema**.

During data loading, it's frequent to use auxiliary objects commonly named **staging**.
It's a temporary storage area that holds data before it is loaded into the data warehouse.


### Fabric

Ingest data in Fabric warehouse is achieved with Pipeline, Dataflows, cross-database querying and COPY INTO command but first, table must be created in SQL.
Generally data are coming from a lakehouse.
Tables can be clone with "zero-copy", just pointing to the data in the OneLake.

Item permissions:
Read: Allows the user to CONNECT using the SQL connection string.
ReadData: Allows the user to read data from any table/view within the warehouse.
ReadAll: Allows user to read data the raw parquet files in OneLake that can be consumed by Spark.


### Security

- **workspaces roles** for access within the workspace as Admin, Member, Contributor and Viewer.
- **Item permissions** at the warehouse level to simplify the sharing of the Warehouse.
- **Data protection security** for more precise control using T-SQL to grant specific permissions to the users.

Dynamic Data Masking: Hide sensitive data in the result set of a query over designated columns.
Offer pre defined functions as Email, Custom text or random.
It doesn't prevent again the inference of the data but only hide it in the result set.

Row-Level security: Filter rows in a table based on the user executing the query.
Ex: A user can only see/update/delete the data of his department.
It is using **security policy** and **predicate function**.
ex:
```sql
/*Create the security predicate defined as an inline table-valued function.
A predicate evaluates to true (1) or false (0). This security predicate returns 1,
meaning a row is accessible, when a row in the SalesRep column is the same as the user
executing the query.*/   
--Create a function to evaluate who is querying the table
CREATE FUNCTION rls.fn_securitypredicate(@SalesRep AS VARCHAR(60)) 
    RETURNS TABLE  
WITH SCHEMABINDING  
AS  
    RETURN SELECT 1 AS fn_securitypredicate_result   
WHERE @SalesRep = USER_NAME();
GO   
/*Create a security policy to invoke and enforce the function each time a query is run on the Sales table.
The security policy has a filter predicate that silently filters the rows available to 
read operations (SELECT, UPDATE, and DELETE). */
CREATE SECURITY POLICY SalesFilter  
ADD FILTER PREDICATE rls.fn_securitypredicate(SalesRep)   
ON dbo.Sales  
WITH (STATE = ON);
GO
```

Column-Level security: Hide columns in a table based on the user executing the query.
It is based on **role** and permissions applied to role.
Calculation on the column is no more possible which is really restrictive compare to the usage of a view.

Using the data control language (DCL) of T-SQL it's also possible to `GRANT`, `DENY` or `REVOKE` permissions on the database objects.
This allows to remove user for ex `SELECT` capabilities and provide `EXEC` capability on a store procedure.

Note: The REVOKE statement can be used to remove granted permissions, and the DENY statement can be used to prevent a principal from gaining a specific permission through a GRANT.

## Real-time analytics

Run analytics queries on raw directly, visualize them and defined alerts usinig KQL.

Components:
- Event house: Kind of database capable of storing and analyzing large amounts of data incoming in real-time.
- KQL database: Kusto database to store collection of tables, functions, materialized views, etc.
- KQL queryset: to run and manipulate data using KQL.
- Real-Time dashboards: to visualize data in real-time.
- Eventstream: Handle live data without coding.

## Administration

The **admin portal** allows to monitor workspace, users, items and sharing.

Admin can define "endorsment" to designate a items trusted and approved at the organization level.
It allow to promote items and make them available to all the organization.
Items can also be "certified" to indicate that they are approved by a designated reviewer.
Certification is enable by the admin then only the reviewer can certify the item.
Promotion can be done by any member of a workspace with the permission.
