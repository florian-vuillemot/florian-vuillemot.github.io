Today, most software are using open-source libraries and managed and control them strictly.
Open-source libraries are also relying on open-source libraries but with another difficulty: they have to be as compatible as possible.

## Context
[Taipy](https://taipy.io) is an open-source library designed to streamline the development of data-driven applications.
As a library, customers considered Taipy as a dependency and managed it strickly.
But what Taipy users' forget, it that Taipy is also using open-source libraries.
Let's take the example of [Pandas](https://pandas.pydata.org/).
Taipy uses Pandas and so when a user install Taipy it also installs Pandas.
Well, normal behavior, but what version of Pandas should Taipy use?
And - more importantly - which version of Pandas are using Taipy users?
There is no easy answer to this question because the solution will depend on three factors: *usability*, *reliability* and *security*.

### Usability
Restriction on dependencies must be as low as possible to let users use the library in most context.
Ex: when released, the latest version of Pandas was not available on all cloud platform as Databricks or Dataiku.
Forcing users to use the latest version of Pandas would had a bad impact on the community using those platform with the Taipy.

### Reliability
When a new version of a dependency is released, it can break the code of the library.
Libraries as Pandas strictly defined versionning and impact on users but it is not always the case.
Some libraries can break their API at the same time then a security fix which put consumers in a stressfull situation because they have to update their code to provide the security fix.
And of course, libraries are not always well tested and can introduce bugs which must be discover as soon as possible to limit the users impact.
When Pandas released the version 2.0 they respect their versionning convention and so, Taipy users were stuck in a old version of Pandas (prior to 2.0) until Taipy was compatible with it.
The reliability of Taipy wasn't impacted but the usability was.

### Security
Security is a major concern for any software.
When a security fix is released, it is important to update the library as soon as possible to limit the risk of being hacked.
Latest version is not always the most secure version and so, sometime, using the previous still supported version is the best security choice.
When Pandas released a security fix, Taipy users want it as soon as possible without waiting a new release of Taipy.
They must have the flexibility to update security fix when they want without being blocked or introduce bugs.
And it is also true for Taipy security fix which must not break the user code.

## Our approached
As the community was growing, the Taipy team has to find a way to manage dependencies in a more efficient way.
Them decided to create a process and a tool to manage dependencies in a more efficient way.

### The process
At the beggining of each sprint, a bot creates a Pull Request to update dependencies and report unmaintained libraries based on the latest update.
This Pull Request contains updated dependencies and tests with the lowest and the latest version of dependencies.
In case of error, an issue can be created and handle during the sprint.

### What do you mean by "lowest and latest version of dependencies"?
Before starting this process, Taipy developers were working with the lowest supported version of dependencies and the CI ran with those versions too.
So another dependencies file was created specifying the latest version supported by Taipy and include it in the CI.
Consequently, the CI runs tests at the two extremety of the supported versions of dependencies.

But the latest version supported is not the latest version available.
Consequently, another CI was created to run tests without any restriction on dependencies.
Doing so, let retrieve the exact latest version of dependencies that are compatible with Taipy because the dependencies manager install the maximum version possible.
And that was really interesting, keeping the Pandas example the Team released that even if the lib was compatible with the newest version of Pandas, a normal installation lead to an old version of Pandas.
So even when Taipy was compatible with the version 2.0 of Pandas as said in our dependencies file, this was not the case in real life which is a big thing from the user point of view!
Relasing that was a big step for the team and the community that lead to work because the compatiblity with Pandas was extremely important and also provide a clear visibility on what we were using.

## Improvements
The major improvement for the Taipy team would be to run test with the middle version of dependencies.
Unfortunatly, the complexity is far more complex due to the huge number of combination and only using random version doesn't look to make sens.

Another interesting improvement would be to let the bot doing the same job on previous Taipy released.
Currently, only security fix are backported to previous version of Taipy.

## Conclusion
Managing dependencies in an open-source library can be a complex task especially when dealing with dependencies that are not well maintained or not rigourous with their version control.
The Taipy team has been able to manage this complexity by creating a process and a tool to manage dependencies in a more efficient way improving the community satifaction.
